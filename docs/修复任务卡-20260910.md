## 5. R01 / P1：人物查询和批量合并只能作用于所选人物

入口：app.py 的 people()（约 1306–1337 行）；web/app.js 的 pickMergeTarget()、resolveMergeTarget()、openQuickName()、批量合并事件（约 223、224、235、286 行）。

### 原因与修复要求

当前 grouped 字符串已经以 GROUP BY p.id 结尾，随后追加 AND p.id IN (...)，该条件被当成分组表达式的一部分，并非筛选条件。前端又把返回的普通分页人物也放进目标候选池。

1. 分开构建 WHERE、GROUP BY、ORDER BY。查询参数与占位符按实际出现顺序组合，不在完整 SQL 尾部盲目追加条件。
2. 保留 /api/people 的兼容语义：普通分页 items 加上显式 ids 所需的补充人物，合并去重；total 仍是普通筛选条件的总量，不能把 extras 加进 total。显式 ids 补查要跨越分页限制；必须符合 ignored 模式。搜索只限制普通分页，显式选中的合法人物不应因搜索词变化而丢失。
3. ids 要去重并保留现有最多 100 个的接口边界；不能悄悄截断后继续合并。UI 若允许选超限，须在写入前给出明确限制提示。
4. 前端先用 selectedIds 过滤候选池。目标必须属于所选集合、确实存在、符合当前人物模式；未取得任意一个所选人物时先报错，不开始写入。
5. 明确目标选择规则：优先所选集合内已确认且有姓名的人；同级按 photo_count 降序、id 升序，保证稳定。保留现有“不把正常人物合并进未恢复路人组”的限制。
6. openQuickName() 按 id 找补查结果，不能用 items[0] 猜测对象。检查所有使用 ids 补查的调用点。
7. 提交前再检查 target.id 在 selectedIds 中；所有实际合并源也必须来自该集合。不要引入自动合并未勾选相似人物的功能。
8. 提交期间禁用重复提交，finally 恢复按钮。现有逐个合并接口可保留；若中途失败，应准确说明哪些已完成、哪些未完成，不写“全部失败”或“全部完成”，不自动猜测并回滚人工信息。

6. 物体入口仍隐藏、没有新扫描；旧标签保留。模拟库写入测试不发往 8765。
7. 为合成原照片计算前后 SHA256，保持不变；隔离库 integrity_check=ok、foreign_key_check 无行。不得以正式库文件哈希变化判断是否违规，因为用户/后台可能仍在正常操作正式库。

### 14.4 完成判定

以下同时满足才能标记“执行完成，待独立复核”：

- R01–R09 所有必做事项和用例有实际证据，R10 的静态、隔离功能、当前页面验收完成；没有把待做、SKIP、BLOCKED 写成 PASS。
- 交付包含实际修改文件、测试脚本、可复跑命令、原始结果、迁移/恢复验证、剩余问题及正式服务是否仍运行旧后端的说明。没有越界数据操作。

如某一项受环境或实现阻塞，整体状态写“部分完成”，逐项列出影响；不要因达到重试上限就把目标标记完成。代码位于工作区但正式服务未重启，应写“隔离环境已验收，正式后端尚未加载”，不能声称正式全流程已上线。

## 15. 进度、失败处理与防止虚假通过

- 每项先建立能捕捉旧问题的检查，保存旧实现失败和新实现通过的输出。若开工已被修复，记录当前满足，并用隔离故障注入或小范围反向验证证明检查会失败；绝不为造红灯改正式源码或正式数据。
- 测试必须调用最终现役函数/模块；可以 mock 模型、网络延时、测试 IO 故障，不能 mock 被验收的 SQL、排序算法、数据库事务和浏览器动作来替代它们。
- 不删测试、不放宽断言、不把所有异常改为成功、不隐藏 toast/日志、不用固定响应/硬编码 fixture ID 通过验收。
- 相同问题连续修复复测失败最多 3 轮。第三轮仍失败，保存日志、判断原因，撤回本项造成的已证实回退或隔离未完成改动，记 BLOCKED，转不依赖它的项目。依赖被阻塞的项目也不能标完成。
- 每一轮记录“新证据→修改→复测结果”。不能无依据重复相同命令，也不以增加等待时间掩盖锁死或错误。
- 只停止本次创建且已核实 PID/端口/数据目录的临时服务；只清理本次生成且无证据/恢复用途的文件。保留故障日志、源码快照和最终截图。
- 完成后不要继续自发修未列入本卡的地图弹窗自动关闭、物体批处理、全量搜索、模型迁移或历史目录整理。记录为后续建议即可。

## 16. 必须交付的文件与报告格式

报告目录：validation/reports/code-quality-repair-20260910/。

| 文件 | 内容 |
| --- | --- |
| PROGRESS.md | 开工回执、R00–R10 状态、当前依赖/阻塞、每次续做位置 |
| BLOCKED.md | 当前阻塞；没有则明确写“无”，保留已解决阻塞的处理记录 |
| COMPLETION.md | 复制 docs/修复完成报告-模板.md 后填写，作为人工复核入口 |
| results.json | 每个用例 ID 的 PASS/FAIL/SKIP/BLOCKED、命令、退出码、证据相对路径和实际期望/结果 |
| manifest.json | 开工与完成源码 SHA256、修改/新增文件、解释器及运行依赖版本、最终测试源码指纹 |
| before/、logs/、screenshots/、benchmarks/ | 开工源码快照，红→绿原始输出，现役页面截图，性能原值与计划 |

results.json 示例结构（示例不是已发生的结果）：

    {
      "task_id": "PHOTO-REPAIR-20260910",
      "overall": "PARTIAL",
      "source_manifest": "manifest.json",
      "cases": [
        {
          "id": "R03-A",
          "status": "NOT_RUN",
          "command": "node validation/repair_viewer_checks.js",
          "exit_code": null,
          "expected": "200 后一次前进显示 201",
          "actual": "尚未执行",
          "evidence": [],
          "verified_at": null
        }
      ]
    }

枚举可用 NOT_RUN、PASS、FAIL、SKIP、BLOCKED；overall 只用 PARTIAL 或 READY_FOR_REVIEW。执行者不能把自己的结论写成“独立复核通过”。

每次改动完成后更新源文件哈希；测试输出必须对应最终文件。如果最终测试后又改了相关实现，必须复测受影响的用例，不能沿用旧 PASS。

最终对用户的消息只需说明：整体状态、修了什么、哪些实测通过、哪些未完成/未正式加载，以及 COMPLETION.md 的绝对路径。不要让用户手工整理散落的证据。
