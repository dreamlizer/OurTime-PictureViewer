## 3. 已确认修复

### 3.1 初始化顺序及样式函数旧变量

`const faceLabels = window.OurTimeFaceLabels || {}` 已提前到 `FACE_LABEL_PLATES` 读取之前。原顺序在 Node 负对照中仍能重现 ReferenceError，新顺序通过。

`applyFaceStyle()` 已按不同职责使用 `requested` 和 `effective`，不再引用未定义的旧 `theme`。在带主题选择、字体、字号、透明度等控件的测试 DOM 中，四个主题的函数调用均未产生前述运行错误。

这证明相关阻断点已消除，不是对完整应用其余路径作无异常保证。

### 3.2 本机字体预览参数同步

新增 `syncLocalFontPreviewAppearance()`，把当前查看器的主题属性及 `--face-*` 变量同步到独立字体弹窗。

采用默认主题的合法自定义值、中文姓名、scale=1，实测如下：

| 参数 | 标签 | 主样式预览 | 本机字体预览 |
|---|---|---|---|
| 字号 | 22px | 22px | 22px |
| 方向 | vertical-rl | vertical-rl | vertical-rl |
| 留白 | 5px 3px | 5px 3px | 5px 3px |
| 底色 | rgba(60,90,100,0.8) | 相同 | 相同 |
| 圆角 | 4px | 4px | 4px |
| 测得宽高 | 34.390625 × 59.53125 | 相同 | 相同 |

off/with/only 对应的本机字体预览文字也一致。本测试没有下载或打包字体，font-family 字符串与几何一致不等于跨机器实际字体覆盖一致。

还有一个低优先级的选择器细节：本机字体预览 `backdrop-filter` 为 none，照片和主预览为 blur(2px)。这不影响上述参数同步修复的结论，但说明不能把“关键参数已一致”写成“所有视觉属性均完全相同”。在下述 CSS 收尾时一起核验即可，不必另开重构。

### 3.3 首次底板失败与恢复

分别模拟素笺 7.png、茶棕 8.png 失败。第一次失败后，无需再打开菜单或手动重选，即得到：

- 实际主题 classic；13px；深底 rgba(20,24,18,0.5)；10px 圆角；中文留白 5px 3px。
- 请求主题仍保留 ivory/tea，序列化偏好不被永久改成 classic。
- 可见回退提示出现。
- 短时持续观察未见无界探测或重绘。模拟茶棕失败时，资源请求序列为 4.png、8.png、8.png；这是有限复查，不是无限循环。
- 解除模拟失败后重选原主题，可以恢复，提示清除。

这是异步状态与样式应用的验证；不包括真实底板图形品质或导出后的边角。

### 3.4 人物状态、偏好及恢复默认

使用两个不同有效 faceId、相同无效 personId（null、空字符串、0、负值、小数、非数字）时，不再静默合并计数；相同有效 personId 的两个 faceId 仍按一人计算。

英文姓名与英文别名组合在 off/with/only × auto/horizontal/vertical 中保持横排。字符串 ignored='0'/'1' 的状态判断一致。

null、损坏 JSON、数组、字符串等偏好，在本次摘录初始化路径中没有产生旧的属性访问异常。恢复外观默认在组件状态层面保留方向、别名模式、姓名显示开关和幻灯片间隔；正式位置 API 与后台保存队列不在此断言范围。

## 4. 剩余 S01｜默认主题横排标签仍被旧 CSS 覆盖

**性质：原有样式未收口，正常显示路径可见；不是本次提交新引入的启动级错误。**

源码：`web/viewer-overrides.css` 中这两组现役规则：

```css
#detail-dialog .face-name-layer.horizontal .face-name {
  padding: calc(var(--face-padding-y) - 1px)
           calc(var(--face-padding-x) + 1px);
}
#detail-dialog .face-name-layer .face-name.is-horizontal {
  padding: calc(var(--face-padding-y) - 1px)
           calc(var(--face-padding-x) + 1px);
}
```

它们优先于 `web/face-labels.css` 的基础共享留白规则，且没有乘 `--face-scale`。当前正式标签构造代码设置了 scale 和方向 class，没有用内联 padding 覆盖这两条旧规则。

默认主题、同一英文名：

| 条件 | 标签 padding | 主预览 padding |
|---|---|---|
| scale=1，同倍率比较 | 4px（四边） | 5px 3px |
| 标签 scale=0.5 | 仍然 4px | 基础预览仍为 scale=1 |

缩小后的字号是 6.5px，但留白仍固定为 4px，破坏了字、底板、留白同比缩放的要求。同倍率下两处配方也不一致。

### 收尾要求

1. 查明并移除/限制这两条对已命名标签生效的旧规则，让横排的标签、主预览、本机字体预览使用同一份配方。
2. 不靠文件末尾再加高权重或 `!important` 硬盖；保留未命名标记原固定尺寸。
3. 可以保持当前共享配方；若明确选择横排应采用不同留白，也必须在共享规则中定义一次，并在所有方向入口同样生效。
4. 以 1、0.5、1.6 三个倍率验证。采用基础 5px/3px 时，0.5 应为 2.5px/1.5px；不能直接把另一个固定数值当修复。
5. 重测默认主题中文强制横排、英文自动横排、中文竖排，以及素笺/茶棕/暗朱，防止影响它们各自的留白和切片。
6. 顺带核验本机字体预览的 blur 等主题专属规则。保持本机字体试选能力，不扩大到新的字体产品功能。

## 5. 剩余 S02｜回退期间控件可操作，却没有对应显示效果

**性质：底板缺失时的低频交互不一致，不是首次回退失败。**

源码：`applyFaceStyle()` 在 effective != requested 时，用完整 classic 默认值绘制；但控件仍启用，`updateFaceStyle()` 写的是请求主题的偏好。

本次模拟素笺和茶棕回退后，再请求修改字号到 18：

```text
字号控件 disabled：false
viewer.faceStyle.fontSize：18
控件最终显示：13
实际标签字号：13px
```

用户可以拖动滑块，但面板和画面回到 13；原请求主题的偏好却被改到 18。这是当前行为与操作反馈不一致。

### 推荐最小收尾

在资源暂不可用、正在使用临时默认外观时，禁用不能作用于当前显示的外观控件，并用一句提示说明原因。保留主题选择、重试以及原有方向/位置操作。资源恢复后依据请求主题能力恢复控件。

不要为了这条低频路径再新建另一套可持久化的回退主题编辑器；也不要默默抹掉原主题设置。采用其他方案时，必须说明控件编辑的是哪套参数，并保持界面反馈一致。

复验：缺图→回退→尝试外观调整→恢复图→返回原主题，检查禁用/提示/数值/偏好；普通资源正常状态下控件仍按原合同工作。
