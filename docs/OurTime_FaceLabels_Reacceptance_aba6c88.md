## 4. R01｜先使用 faceLabels，后声明 const：启动即报错

**优先级：P0，先修。**  
**来源：** `web/viewer.js` 文件开头，`FACE_LABEL_PLATES` 与 `faceLabels` 声明。[S1]

当前顺序：

```javascript
const FACE_LABEL_PLATES=faceLabels.PLATES||{ /* fallback */ };
const faceLabelThemeReadiness=new Map();
const faceLabelEffectiveThemes=new Map();
const faceLabels=window.OurTimeFaceLabels||{};
```

Node 和 Chromium 都复现：

```text
ReferenceError: Cannot access 'faceLabels' before initialization
```

即使 `window.OurTimeFaceLabels` 已经存在，读取当前脚本里的 `const faceLabels` 仍会在初始化前报错。这里不是把模型脚本提前加载一下就必然解决，也不是 `|| {}` 能兜底的情况。

**影响：** 当浏览器重新执行这份 viewer.js，后续顶层初始化和事件绑定无法正常完成。已经打开的旧页面可能仍保留此前的内存代码，但本报告未核实用户页面是否属于这种情况。

**修复要求：** 将模型绑定放在所有依赖读取之前，保证入口明确。不要改成一堆可变全局变量绕过错误，不要用 try/catch 吞掉后继续运行半初始化界面。

**复验：** 用全新浏览器 context 加载修改后真正的 index.html 与脚本，模型正常加载、默认偏好和已保存偏好均可打开照片、出现工具与标签；监听 pageerror。不得仅运行 node --check，原错误代码本身可以通过语法检查。

## 5. R02｜applyFaceStyle 改了变量名，后半段仍引用 theme

**优先级：P0，与 R01 独立。**  
**来源：** `web/viewer.js`：`applyFaceStyle()`。[S2]

函数前面已改成：

```javascript
const requested = /* ... */;
const effective = /* ... */;
```

后面却仍有：

```javascript
if(themeSelect) themeSelect.value=theme;
syncFaceFontSelect(family,s,theme);
ensureFaceLabelThemeAvailable(theme);
```

以及主题按钮、字体提示和控件权限等多处旧 `theme` 引用。函数内已没有对应声明。

在独立提供所需 DOM/状态依赖后，执行到第一个旧引用得到：

```text
ReferenceError: theme is not defined
```

**影响：** 即使修复 R01，样式面板初始化/样式更新仍可能在这里中断。不能只挪动第一处声明，就宣布恢复正常。

**修复要求：** 按语义统一替换，不是临时加一个不明确的 `theme` 全局量。

- 用户选择及保存意图、需要探测的资源，对应 requested。
- 实际绘制参数、实际使用的底板与字体，对应 effective。
- 回退期间控件如何表现要明示：不能把默认主题参数写回用户请求主题，也不能显示可操作但无效果的控制项。
- 普通显示控件需要反映用户真实选择；当前回退状态另作轻提示。

**复验：** 四主题切换、恢复外观默认、打开/关闭面板、只有别名预览、资源失败及恢复，均不得抛未定义变量错误。必须走 UI 原入口，不可把测试直接指向新的纯函数绕过查看器。

## 6. R03｜字体弹窗方向修了，当前外观变量仍没有传过去

**优先级：P1，正常可见路径。**  
**来源：** `web/viewer.js` 的 `applyFaceStyle/openLocalFontDialog/updateLocalFontPreview`；`web/face-labels.css`；`web/viewer-overrides.css` 的根变量。[S2][S3][S4]

有效改进：独立字体弹窗现在能匹配基础共享选择器；旧固定 20px 规则已删除；中文预览在本次 CSS 复现中正确竖排，别名示例选取也有修复。

剩余问题：字体弹窗仍是 body 的直接子元素；字号、颜色、背景、圆角、留白等自定义变量只写到 `#detail-dialog`。给字体弹窗设置几个 data 属性，不会让它继承另一个兄弟元素的 CSS 变量。

使用合法的默认主题自定义参数，在基础倍率 1 下实测：

| 属性 | 照片标签 | 主面板预览 | 本机字体预览 |
|---|---|---|---|
| 字号 | 22px | 22px | **13px** |
| 方向 | vertical-rl | vertical-rl | vertical-rl |
| 内边距 | 5px 3px | 5px 3px | **5px** |
| 背景 | rgba(60,90,100,.8) | 同左 | **rgba(20,24,18,.5)** |
| 圆角 | 4px | 4px | **10px** |

**修复要求：** 将当前有效视觉参数通过统一入口应用到独立弹窗；试选字体作为唯一有意的局部差异。可使用共享视觉宿主类＋同一参数写入函数，或复制受控变量集合；不要再维护第二份预览默认值。

只需保持默认主题原有的本机字体选择能力，不借机开放其他主题的任意字体，也不改全站字体。仍需检查所有相关主题选择器是否匹配其真实宿主，不只是基础字号规则。

**复验：** 默认参数一次，自定义 22px、字色、底色、透明度和圆角再一次；同倍率、同字体时三个位置 computed style/尺寸一致。只有别名、with/only 模式均显示正确文字；取消不改变用户设置，确认后实图与保存结果一致。

## 7. R04｜首次异步检测到缺图，仍只改状态，不重新应用外观

**优先级：P1，故障回退路径。**  
**来源：** `ensureFaceLabelThemeAvailable()`、`applyFaceStyle()`、`renderFaceNames()`。[S2][S5]

新增 `applyFaceStyle` 能根据已知有效主题选择 classic 参数，但资源失败回调仍然只做：

```text
更新有效主题缓存 → 改 data-face-theme-effective → 写提示 → renderFaceNames
```

所核对的 `renderFaceNames()` 不重新应用主题 CSS 变量。因此首次探测失败时，状态虽写 classic，字号与背景仍然沿用旧主题。

用当前回调原文注入“茶棕横牌 8.png 缺失”，复现结果：

```text
用户请求：tea
根元素 data-face-theme：tea
根元素 data-face-theme-effective：classic
实际字号：16px
实际背景：rgba(126,98,75,.66)
实际圆角：0px
实际留白：9px 6px
```

预期 classic 不是这套参数。下一次另行触发 applyFaceStyle 可能更新参数，但用户不应靠再点一次菜单才完成回退。

**修复要求：** 将探测和已解析状态的应用分开；回调根据当前有效版本更新实际样式、预览和必要重排。避免 `applyFaceStyle → ensure → applyFaceStyle → ensure` 无限循环。资源恢复也必须经过同一条有界链路，保留用户请求主题与自定义偏好。

**复验：** 仅阻断 7 或 8、全部缺失、恢复三类；第一次失败返回后不做额外点击，直接检查内容、计算样式和可见提示。不能只断言一个 dataset 值。修复后的主题导出也要与屏幕有效状态一致。

## 8. R05、R06｜保留在同一轮的小型收口事项

### R05：空人物 ID 被转换成零

`faceLabelIdentity()` 当前使用 `Number(face.person_id)` 后检查 `Number.isFinite`。缺省 undefined 已能走 face ID 回退，但显式 null 会变成 0；两张 face ID 不同、person_id=null 的合成脸仍被统计为一个人。[S6]

这不是已证明的正式库错误。最小修法是先验证值存在且符合当前接口有效 ID 合同，再按 person ID 去重；否则按有效 face ID 分开处理或做明确诊断。不更改真实人物关系。

### R06：唯一来源仍需完成

`viewer.js` 开始使用 `faceLabels.PRESETS/PLATES`，但整份 fallback 主题表与资源表仍在；缩放函数仍独立实现，模型也有另一份。切片参数仍由 CSS 与模型各自描述。[S1][S3][S7]

先修运行错误，再在全仓引用核查后删真正失效的副本；对必要迁移保留明确入口。不要用“模块没加载时再跑另一套完整系统”的方式重新引入双轨。无需另建框架，不以删行数为目标。
